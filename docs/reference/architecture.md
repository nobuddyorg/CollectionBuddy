# Architecture reference

Technical description of how CollectionBuddy is put together. For _why_ it's built this way, see [Design decisions](../explanation/design-decisions.md).

## Application

- **Next.js, static export** (`output: 'export'` in [`web/next.config.ts`](../../web/next.config.ts)) — there is no server runtime and no route handlers. Every page except `layout.tsx` is a client component; `layout.tsx` renders once at build time, before any user session exists.
- `basePath` is `/CollectionBuddy` in production builds (`NODE_ENV === 'production'`, i.e. CI) to match GitHub Pages serving the site from `https://<org>.github.io/CollectionBuddy/`, and empty in local dev. Exposed to client code as `NEXT_PUBLIC_BASE_PATH`.
- The Supabase client ([`web/src/app/supabase.ts`](../../web/src/app/supabase.ts)) is created once at import time, with `flowType: 'pkce'` (so auth tokens never land in the URL fragment), `persistSession`, `autoRefreshToken`, and `detectSessionInUrl` all on.
- All authorization is enforced by Postgres Row Level Security — there is no server-side authorization code to bypass, because there is no server.

## Database schema

Defined across [`supabase/migrations/`](../../supabase/migrations/), applied in filename order. The baseline is seven files (0001 to 0007), ordered by dependency rather than by history: extensions, functions, tables, triggers, indexes, policies, storage. None of those seven patches another, so within the baseline, what a file says is what the database has.

The second squash (#580) folded the then-current 0001 to 0014 back down into these seven, so features that had arrived as migrations of their own — account sharing, the shared-photograph policies, the `images` table, the editor role — are now spread across whichever file owns that kind of object, rather than each having a file to point at. Where a section below would once have named such a file, it names the baseline file the thing actually lives in.

Five migrations have landed on top of that baseline since, every one of them a correction to the authorization boundary, and each does patch what the baseline says:

| File | What it changes |
| --- | --- |
| [`0008_storage_no_update.sql`](../../supabase/migrations/0008_storage_no_update.sql) | Drops `authenticated`'s `UPDATE` on `storage.objects` and the `update shared objects` policy: the policy re-tested only the item-id segment of the path, so an update rewriting the uid segment carried an owner's photograph into an editor's namespace. An object's path can no longer change at all. |
| [`0009_caller_email_trim.sql`](../../supabase/migrations/0009_caller_email_trim.sql) | `caller_email()` trims as well as lowercases, so both sides of the sharing-email comparison normalize the same way. Fail-closed before, but a legitimate grantee could be denied silently. |
| [`0010_storage_pin_upload_prefix.sql`](../../supabase/migrations/0010_storage_pin_upload_prefix.sql) | `write shared objects` now constrains the uid segment too, so an editor cannot create an object under the owner's prefix. |
| [`0011_least_privilege_grants.sql`](../../supabase/migrations/0011_least_privilege_grants.sql) | Revokes `anon`'s remaining privileges on `category_shares` — the one table 0006 omitted — and narrows `authenticated` to the DML its policies actually back. |
| [`0012_images_path_matches_item.sql`](../../supabase/migrations/0012_images_path_matches_item.sql) | A check constraint tying an `images` row's `path_full` to the item it names (`storage_item_id(path_full) is not distinct from item_id`), so a row can no longer point at another user's object or at something that is not a storage path at all. |

Keeping the baseline readable that way is a maintenance job, not a property. See [Design decisions](../explanation/design-decisions.md#why-the-migrations-were-squashed) for why, and the [Developer guide](../how-to/developer-guide.md#squashing-migrations-again) for what squashing again would take.

### Row Level Security

This is the _only_ authorization layer — see [Design decisions](../explanation/design-decisions.md#why-authorization-lives-entirely-in-postgres-rls). Everything is in [`0006_policies.sql`](../../supabase/migrations/0006_policies.sql), built out of an owner check and two `security invoker` predicates declared at the top of that file:

- `user_id = (select auth.uid())` — the owner check every policy starts from. The scalar subquery is deliberate: it makes the planner evaluate the call once per query rather than once per row.
- `has_category_read_access(cat_id)` — an active `category_shares` grant to the caller's own email, at either role.
- `has_category_write_access(cat_id)` — ownership of the category, **or** an active grant at role `editor`.

Ownership is bundled into the write predicate and deliberately left out of the read one; every read policy keeps its own owner check as a separate `or` branch instead. Bundling ownership into the read predicate too would let a category's owner see every item merely linked into that category, including ones an editor added that the owner was never otherwise granted visibility into. The two are asymmetric on purpose — don't "simplify" one to match the other.

| Table             | `select`                                        | `insert`                                         | `update`                                     | `delete`                                         |
| ----------------- | ----------------------------------------------- | ------------------------------------------------ | -------------------------------------------- | ------------------------------------------------ |
| `categories`      | owner, or read access                           | owner                                            | owner                                        | owner                                            |
| `items`           | owner, or read access via a linked category     | owner                                            | owner, or write access via a linked category | owner, or write access via a linked category     |
| `item_categories` | owner, or read access to the category           | owner (the item's)                               | —                                            | owner, or write access to the category           |
| `category_shares` | owner, or the invited email                     | owner                                            | owner                                        | owner, or the invited email                      |
| `images`          | owner, or read access via the item's categories | owner, or write access via the item's categories | —                                            | owner, or write access via the item's categories |

Neither `item_categories` nor `images` has an `update` policy — a mapping row and a photograph row both have nothing to edit once written — and with RLS on, no policy means no row matches, so the omission _is_ the denial. `images` is also the one table granted just `select, insert, delete`; the rest carry all four.

Category-level actions stay owner-only at every role. An `editor` grant widens access to item _content_ inside a shared category; renaming that category, deleting it, and managing its shares are never widened by it.

No role is named on any policy, so each applies to every role that can reach its table. RLS alone would deny `anon` regardless, since `auth.uid()` and `auth.jwt()` are both null there and no predicate can be satisfied without one. The file additionally revokes `anon`'s table privileges outright on `categories`, `items`, `item_categories` and `images`, rather than leaving the predicate as the only thing standing between it and those tables — Supabase's project bootstrap grants `anon` default table privileges, so the revoke makes the denial explicit instead of inherited. `category_shares` was the one table missing from that list; [`0011_least_privilege_grants.sql`](../../supabase/migrations/0011_least_privilege_grants.sql) adds it, so all five are now covered twice over.

That migration also brings `authenticated`'s privileges down to what 0006 always claimed they were ("deliberately narrow: usage plus DML on each table"). They were not: the same bootstrap grants all privileges on public tables, so `TRUNCATE`, `REFERENCES` and `TRIGGER` sat on all five alongside the DML, and `UPDATE` sat on `item_categories` and `images`, which deliberately have no update policy. `TRUNCATE` is the one that mattered — RLS does not filter it, so the privilege meant "empty this table, every user's rows included", and executing it as `authenticated` against a local stack did exactly that. It was never reachable, since PostgREST exposes no `TRUNCATE` verb and there is no other way to run arbitrary SQL as that role; it is the same defence-in-depth argument as the `anon` revoke, not a patched hole.

The same file ends with an assert-rather-than-assume guard on `storage.objects`: a `do` block that raises at migration time if row-level security is ever found disabled there, since [`0007_storage.sql`](../../supabase/migrations/0007_storage.sql)'s grants to `authenticated` only narrow down to "your own objects" because RLS is on. It reads `pg_class` rather than running `alter table ... enable row level security`, which needs `supabase_storage_admin` and would fail every migration after it.

`web/e2e/signed-in/rls.spec.ts` is the executable version of this section: it asks the questions the app never would, with a real token, against a local stack. It covers owner-versus-stranger and `viewer` grants — `editor` grants are not covered there yet, see [TEST_STRATEGY.md](../../TEST_STRATEGY.md).

### Sharing

Account-based, one category at a time, at one of two roles (#483). No public/anonymous links — see [Design decisions](../explanation/design-decisions.md#why-sharing-has-no-public-link) for why that was ruled out.

- **Roles.** `category_shares.role` is `viewer` or `editor` (a `check` constraint allows nothing else), defaulting to `viewer`. A viewer reads the shared category, its items, their links and their photographs. An editor additionally adds, edits and deletes items and photographs inside it, via `has_category_write_access()`. Both stop at the category itself — see "Row Level Security" above. `page.tsx`'s `canEditSelected` mirrors this in the interface, but that is UX; the policies are the check.
- **A grant is always created as a viewer.** `useShares.tsx` never sends a role on insert; raising one to `editor` is an update on the existing row, gated by the owner-only "update own category_shares role" policy and by `tg_category_shares_enforce()`, which rejects an update that moves any column other than `role`.
- An owner invites by email; there is no separate accept step and no trigger resolving the invite against `auth.users`. Both predicates compare `category_shares.invited_email` against `public.caller_email()` — the caller's own JWT email, lowercased — so a grant simply starts working the moment its invited email signs in, including the first time, if the invite was sent before that email had an account.
- `tg_category_shares_enforce()` re-derives `owner_user_id` from the category being shared, rejects sharing a category the caller doesn't own, rejects sharing with oneself, and normalizes the email to lowercase — the same shape as `tg_item_categories_enforce()`'s cross-tenant guard.
- One grant per (category, email), enforced by a unique constraint: re-sharing with someone already invited is a no-op, not a second row with its own, different expiry.
- Ending a grant is a `delete` on `category_shares`, from either side: the owner revoking and the grantee leaving are the same operation, permitted by the same policy, on the same row. Nothing tracks a "left" or "revoked" state — once the row is gone, it's gone for both.
- `expires_at` is optional. The `check` constraint on it only requires `expires_at > created_at`, not that either is in the future, so a grant that is already expired is a legal row; what makes it inert is that both access predicates re-check the clock on every read. `select` and `delete` on `category_shares` itself deliberately skip that check, so a dangling expired grant stays visible to both sides to clean up.
- The grant reaches photographs as well as metadata — both the `images` rows and the Storage bytes behind them. See "Storage" and "Images" below.

### Triggers and functions

Functions in [`0002_functions.sql`](../../supabase/migrations/0002_functions.sql), the triggers that fire them in [`0004_triggers.sql`](../../supabase/migrations/0004_triggers.sql). The functions come first because `items.tags_text` is a generated column calling `join_tags()`. Two of them live in [`0006_policies.sql`](../../supabase/migrations/0006_policies.sql) instead: `has_category_read_access()` and `has_category_write_access()` are `language sql`, which Postgres resolves against the catalog at `CREATE FUNCTION` time, so they cannot be created before the tables they query exist. The plpgsql ones can, because plpgsql defers name resolution to first call.

- `normalize_text()` — trims and collapses whitespace, returns `NULL` for anything blank.
- `join_tags()` — space-joins a tag array; backs the `tags_text` generated column.
- `caller_email()` — the caller's own JWT email, lowercased. Every share predicate compares against this.
- `enforce_user_id()` — forces `user_id = auth.uid()` on insert; on update it restores the old owner rather than raising, so an attempt to hand a row to someone else is ignored rather than refused.
- `tg_categories_normalize()` / `tg_items_normalize()` — apply `normalize_text()` to name/title/description/place, and for items also dedupe + sort `tags`.
- `tg_item_categories_enforce()` — verifies the item and category exist, requires `has_category_write_access()` on the target category, sets `user_id` from the item's own owner, and rejects the row if that owner isn't the caller. Owning the category is no longer sufficient on its own, and no longer necessary: an editor may file their own item into a category someone else owns, and nobody can file anything into a category they have no write access to.
- `tg_category_shares_enforce()` — see "Sharing" above.
- `tg_images_enforce()` — re-derives `images.user_id` from the item's owner, and rejects an insert whose item is neither the caller's own nor linked into a category the caller has write access to.
- `delete_item_if_orphan()` — after an `item_categories` row is deleted, deletes the item if it now belongs to zero categories. Runs `FOR EACH STATEMENT` with a transition table (not `FOR EACH ROW`) — see [Design decisions](../explanation/design-decisions.md#why-the-orphan-cleanup-trigger-is-statement-level).
- `tg_set_updated_at()` — stamps `updated_at` on every update of `categories` and `items`, via `trg_categories_updated_at` and `trg_items_updated_at`.
- `storage_item_id()` — parses the itemId out of a storage path, returning `NULL` rather than raising on one that doesn't parse. See "Storage" below for why that distinction matters inside an RLS predicate.
- `keepalive()` — no-op RPC, granted to `anon` and `authenticated`, called daily by [`keep-alive.yml`](../../.github/workflows/keep-alive.yml) to stop a free-tier Supabase project from auto-pausing.

Every one of them pins `set search_path = ''`, so each reference inside is schema-qualified. Without it, a `security definer` function resolves names through the _caller's_ search path, which is how someone able to create objects gets code to run as the function's owner.

Postgres grants `execute` on a new function to `PUBLIC` by default. That default is revoked for the helpers not meant to be reachable as RPCs: `normalize_text()` and `join_tags()` were callable at `POST /rest/v1/rpc/normalize_text` (and `join_tags`) with the anon key until it was, even though neither touches a table. `keepalive()` is the one function `anon` is deliberately granted.

There is no image-cleanup trigger reaching into `storage.objects`. A `cleanup_item_images()` one existed and was removed: Supabase forbids deleting from `storage.objects` outside the Storage API, and the trigger made every item delete fail — see [Design decisions](../explanation/design-decisions.md#why-images-are-deleted-client-side-before-the-database-row). The `images` table is a different matter: it's a plain `public` table this project owns, so its rows cascade away with the item that owned them (`item_id references items(id) on delete cascade`) like any other child row — the client only has to read their paths _before_ that delete, to still remove the Storage bytes afterward.

### Indexes

- Unique `(user_id, lower(name))` on `categories`.
- `(user_id, created_at desc)` on `items`, for list ordering.
- Trigram GIN indexes (`pg_trgm`) on `items.title`, `items.description`, `items.place`, `items.tags_text` — see [Design decisions](../explanation/design-decisions.md#why-search-uses-trigram-ilike-instead-of-full-text-search) for why these exist instead of Postgres full-text search.
- A plain GIN index on `items.tags` for containment filtering, which is an array operation and can't use the trigram index.
- `item_id`, `category_id` and `user_id` on `item_categories`.
- `(item_id, created_at asc, id)` and `user_id` on `images` — the former is both the read path (an item's photographs, oldest-first, matching the ordering `storage.list()` used to guarantee) and what a capture-before-cascade delete filters by; the latter matches `item_categories`' own precedent of indexing `user_id` even though `item_id` already narrows most queries.

Nothing here indexes `storage.objects`, and nothing can: hosted Supabase owns it as `supabase_storage_admin` and doesn't make `postgres` a member, so `create index` on it raises `42501` for every role available to us. Policies on it are fine; DDL is not.

### Storage

Single private bucket, `item-images`, all of it in [`0007_storage.sql`](../../supabase/migrations/0007_storage.sql). Object paths are `<uid>/<itemId>/<file>`, where the uid is whoever _uploaded_ the object. The bucket itself additionally restricts uploads to `image/webp`, `image/jpeg`, `image/png`, capped at 5 MiB — defense in depth in case something calls the Storage API directly, bypassing the client's own compression and file-type filtering. Nothing is served publicly; the client reads through signed URLs.

Five policies: three owner-only, two shared. Postgres ORs every applicable policy, so the shared pair only ever widens the owner-only set — it is not a rewrite of it.

- **Owner-only**, keyed on the path's first segment: `select`/`insert`/`delete` where `split_part(name, '/', 1) = auth.uid()::text`. Each names `authenticated`.
- **Shared**, for a `category_shares` grantee: `select` and `delete` only, each joining through `item_categories` to `has_category_read_access()` for `select` and `has_category_write_access()` for `delete` — the same predicates the mirrored tables use (see "Sharing" above). These are what let a _second grantee_ reach an object that landed under one editor's prefix.

Note which party that does **not** include. `has_category_write_access()` bundles category ownership in, so the owner can `delete` such an object; `has_category_read_access()` deliberately does not, and an owner cannot share a category with herself, so **the owner cannot read or sign an object an editor uploaded** — its first path segment is the editor's uid, and she holds no grant. This is the same asymmetry that keeps an entry an editor filed into a shared collection invisible to that collection's owner (see "Sharing" above); it is long-standing and deliberate at the policy level, but it is worth knowing that a collection's owner sees nothing an editor contributes, photographs included.

There is no shared `insert`, and that is the point: a path is prefixed with the _uploader's_ uid (`imagePrefix`, `data/images.ts`), so an editor's own upload already satisfies the owner-only set, and nothing legitimate ever needs to write under someone else's prefix. `"write shared objects"` used to allow it — it constrained segment 2 and said nothing about segment 1 — which let an editor store bytes of their choosing under the owner's uid: against her quota, served back to her by her own read policy, attributable to her by path alone, and, paired with an `images` row an editor may legitimately insert, rendering as her own photograph of her own entry. Pinning segment 1 would have made it a strict subset of `"upload own objects"`, so it was dropped instead ([`0010_storage_pin_upload_prefix.sql`](../../supabase/migrations/0010_storage_pin_upload_prefix.sql)).

There is deliberately **no `update` on either set**, and `authenticated` holds no `UPDATE` privilege on `storage.objects` at all ([`0008_storage_no_update.sql`](../../supabase/migrations/0008_storage_no_update.sql)). An object's path is fixed from the moment it is written: `move()` and `upsert` uploads are both refused, for the owner as much as for a grantee. That is a security boundary, not tidiness. The shared `update` policy authorized on the path's _second_ segment while the owner-only set authorizes on the _first_, and its `WITH CHECK` re-tested only the second — so an editor could rewrite segment 1 to their own uid and carry the owner's photograph into their own namespace, where revoking the share no longer reached it, the owner could no longer see it, and the sweep (which then keyed on segment 2) did not count it as orphaned. Dropping the capability is what makes the invariant hold; the app never needed it, since `data/images.ts` only uploads, signs and removes.

The shared set cannot key on the path the way the owner-only set does, because the path carries no grantee-checkable identity of its own — it is still `<owner_uid>/<itemId>/<file>`. It extracts the itemId segment instead, through `public.storage_item_id()`, which exists for one reason: a plain `split_part(...)::uuid` raises on any path whose second segment isn't a UUID, and a raised error inside an RLS `USING` clause aborts the whole statement rather than merely failing to match that row. The function catches the cast failure and returns `NULL`, so a malformed path makes that one policy simply not match. The orphan-sweep query in [`cleanup-orphaned-photos.yml`](../../.github/workflows/cleanup-orphaned-photos.yml) sidesteps the same trap by never casting at all — it compares an object's name to `images.path_full` and `images.path_thumb` as text.

An older, hand-written set of four dashboard policies (`list own`, `upload own`, `update own`, `delete own`) predated any of this being in migrations and was still live in production when the first baseline was taken. It tested the same prefix with `left(name, 37)` and named no role, making it a strict subset of what the owner-only four already allow. It was verified redundant rather than merely similar, and is now dropped; the `drop policy if exists` lines stay so a database still carrying them converges.

### Images

`storage.list()` has no recursive/flat listing across prefixes, so discovering what photographs an item has used to mean one Storage API call per item — up to nine sequential round trips just to paint a page of the grid, and a whole retry/concurrency-pool apparatus in `exportCategory.ts` to make the same thing survive at export scale. `public.images` ([`0003_tables.sql`](../../supabase/migrations/0003_tables.sql)) is a queryable index of what's in Storage, written by the client at upload time: one row per photograph, `path_full`/`path_thumb` already complete Storage paths. "What images does this page's items have" is now one indexed query (`item_id in (...)`) instead of one per item.

- RLS mirrors `item_categories`: `select`/`insert`/`delete`, no `update` — a row has nothing to edit once written. All three are additive the same way `categories`/`items`/`item_categories`/`storage.objects` are: owner, or an active `category_shares` grant reached by joining `item_categories` on `images.item_id` (read access for `select`, write access for `insert` and `delete`). That join is a plain one, unlike `storage.objects`' policy, since `item_id` is a native column here rather than something to parse back out of a path string.
- `tg_images_enforce()` is the same shape as `tg_item_categories_enforce()`, with only one owned entity to check: it re-derives `user_id` from the item's own owner and rejects an insert against an item that is neither the caller's own nor linked into a category the caller has write access to. `user_id` still follows the item's owner either way — the write-access branch widens who may _insert_ the row, not whose row it becomes.
- Storage still holds the bytes and is still the authority on what actually exists; this table is written and cleared by the client, never trusted blindly — see the FK-cascade note above for how a row's removal is sequenced against the Storage delete it implies.

## Client data-access layer

[`web/src/app/data/`](../../web/src/app/data/) holds the table and storage queries, plus the two other places the app talks past a UI boundary to something external — the auth client and the Photon gazetteer:

- `items.ts` — `listItems()` (paginated, category-scoped, optional search via `buildSearchFilter()`), `createItem()`, `updateItem()`, `deleteItem()`, `linkItemToCategory()`, `listItemPlaces()`.
- `categories.ts` — `listCategories()`, `createCategory()`, `renameCategory()`, `deleteCategory()`, plus `listItemIdsForCategory()` / `countItemsForCategory()` / `listItemIdsLinkedElsewhere()` used to work out which items a category deletion would orphan, and to warn about how many before it runs.
- `images.ts` — reads/writes the `images` table (`listImagesForItems()` for the grid/export read path, `listImagePathsForItems()` for the capture-before-cascade delete paths, `createImageRow()`, `deleteImageRow()`) plus the Storage-bytes calls that still go straight to Storage regardless of the table (`createSignedUrls()`, 1 hour expiry; `uploadImageObject()`; `removeImageObjects()`), and `imagePrefix()`, the one place the `<uid>/<itemId>` storage-path scheme is written down.
- `auth.ts` — `verifiedUserId()`, which round-trips to the auth server rather than reading the cached session, for a caller about to write bytes under a user-derived path.
- `photon.ts` — the one [Photon](https://photon.komoot.io/) client both geocoding surfaces (`ItemForm/usePhoton.tsx`'s autocomplete, `Map/usePlaces.tsx`'s background lookup of catalogued place names) go through: `photonSearchUrl()`, `photonLang()`, `coordsFromFeature()` and `isRetryableStatus()`. The two used to hit the endpoint independently, with two coordinate validators that disagreed on `NaN`.

It is not the only code holding the client, though. Auth and session work reaches [`supabase.ts`](../../web/src/app/supabase.ts) directly — `useSession.ts`, `page.tsx`, `login/useAuthRedirect.ts`, `login/useGoogleSignIn.ts` — none of which have anywhere else to live, since there is no session-management equivalent of `data/auth.ts`. Nothing under `components/` does; an ESLint rule (`no-restricted-imports`, scoped to `components/**`) keeps it that way.

| Workflow (job)                                                                       | Trigger                            | Does                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [`ci.yml`](../../.github/workflows/ci.yml) (`prek`)                                  | push/PR to `main`                  | The repo-wide hooks from [`.pre-commit-config.yaml`](../../.pre-commit-config.yaml): file hygiene, spell check, shellcheck, markdownlint, and zizmor's security analysis of these workflows.                                                                                                                                                                                   |
| [`ci.yml`](../../.github/workflows/ci.yml) (`build_and_test`)                        | push/PR to `main`                  | Build, type-check, format check, lint, `vitest run --coverage` (gated by thresholds — see [Configuration](configuration.md#coverage-and-mutation-thresholds)), then the signed-out Playwright suite against the built export, served under the base path on desktop and a phone viewport — this replaced an earlier check that only served the export and confirmed it booted. |
| [`ci.yml`](../../.github/workflows/ci.yml) (`e2e_local_stack`)                       | push/PR to `main`                  | Starts a Supabase stack in Docker and runs the signed-in Playwright suite against it: the catalogue, search, the map, the entry forms, photographs, and the row-level security boundary.                                                                                                                                                                                       |
| [`ci.yml`](../../.github/workflows/ci.yml) (`mutation_test`)                         | push/PR to `main`                  | Stryker against the pure, high-risk modules listed in [`stryker.config.mjs`](../../web/stryker.config.mjs).                                                                                                                                                                                                                                                                    |
| [`pages-deploy.yml`](../../.github/workflows/pages-deploy.yml) (`migrate`)           | push to `main`, manual             | Applies any pending migrations to the hosted database and reloads PostgREST's schema cache, before anything that depends on the new schema is built.                                                                                                                                                                                                                           |
| [`pages-deploy.yml`](../../.github/workflows/pages-deploy.yml) (`build`)             | push to `main`, manual             | Builds the static export.                                                                                                                                                                                                                                                                                                                                                      |
| [`pages-deploy.yml`](../../.github/workflows/pages-deploy.yml) (`deploy`)            | push to `main`, manual             | Publishes the export to GitHub Pages.                                                                                                                                                                                                                                                                                                                                          |
| [`pages-deploy.yml`](../../.github/workflows/pages-deploy.yml) (`smoke_test`)        | push to `main`, manual             | Reruns the signed-out Playwright suite against the live deployed site.                                                                                                                                                                                                                                                                                                         |
| [`keep-alive.yml`](../../.github/workflows/keep-alive.yml)                           | daily cron, manual                 | Calls the `keepalive()` RPC to stop a free-tier Supabase project auto-pausing.                                                                                                                                                                                                                                                                                                 |
| [`cleanup-orphaned-photos.yml`](../../.github/workflows/cleanup-orphaned-photos.yml) | daily cron (`30 4 * * *`), manual  | Deletes Storage objects that no `images` row references as either `path_full` or `path_thumb`, older than 48h — the cleanup side of the ordering explained in [Design decisions](../explanation/design-decisions.md#why-images-are-deleted-client-side-before-the-database-row). A manual run is a dry run unless opted out of.                                                |
| [`auto-merge.yml`](../../.github/workflows/auto-merge.yml)                           | PR events                          | Merges Dependabot PRs for patch-level devDependency bumps only, once every required check passes (`gh pr merge --auto`) — it does not itself approve the PR, so a branch-protection rule requiring a review would still block it.                                                                                                                                              |
